# Changelog

## Unreleased

- Add Layer 0h: a sandbox for the [pi](https://github.com/earendil-works/pi-mono) coding agent (`managed-settings/pi/`). pi was the one fleet harness with no read guard at all — no managed settings, no sandbox, and an A2A host that hands dispatched workers the same unfettered `bash`. The layer is two halves: a root-owned `/etc/pi` (Seatbelt profile `sandbox.sb`, wrapper `bash`, `ripgrep.conf`) that the kernel enforces, and a user-owned pi extension (`dependency-safety.ts` → `~/.pi/agent/extensions/`) that routes the built-in `bash` tool through the wrapper (fail-closed when the wrapper is missing), overrides the in-process `read` tool with the same deny set, blocks `write`/`edit` into credential directories and into its own directory, refuses `grep`/`find`/`ls` aimed into credential directories, and points the `grep` tool's ripgrep at the root-owned ignore config.

  Unlike Layer 0f this is a read-PATH guard, not a command-text matcher: the kernel resolves the path, so traversal, symlinks and quoting tricks fail identically with EPERM, and every child process of the command inherits the profile. Verified live 2026-08-30 (pi 0.84.4, macOS 26.3.1): in a `pi -p` session `cat ~/.ssh/<file>` returned `Operation not permitted`, `read` on a fixture `.env` and on a non-existent `~/.ssh/…` path returned the guard's denial while `.envelope` read normally, and a `write` to `~/.ssh/zzz_probe` was blocked with no file created.

  **`~/.npmrc` is exempted from the bash sandbox on purpose.** Denying it makes npm inside the sandbox silently report `ignore-scripts=false` — Layer 1 undone by Layer 0 (measured: `npm config get ignore-scripts` → `false` under the deny, `true` without). Project-local `.npmrc` stays denied; the `read` tool denies `~/.npmrc` regardless. Codex's Layer 0b denies `~/.npmrc` sandbox-wide and has the same exposure — noted in the README, not changed here.

  Limits are stated rather than implied: the extension is user-owned and `pi --no-extensions` skips it (Layer 0g standing, not 0a/0b/0f); the in-process guards do not bind other extensions or MCP servers in the same process; `gh` inside pi's bash loses auth and `.env.example` is unreadable, both by parity with 0a/0b; `sandbox-exec` is deprecated by Apple and still enforced on macOS 26.3.1.

- verify-install.sh gains a Layer 0h section: root ownership and mode checks on `/etc/pi` itself and its three files (a user-writable directory would let the agent replace the profile), then behavioural probes through the real wrapper — `~/.ssh` and a runtime-created `.env` must fail with EPERM, `.envelope` and `/etc/hosts` must succeed, and `npm config get ignore-scripts` must agree inside and outside the sandbox. The installed extension must match the checkout's template byte-for-byte (stale or edited copies FAIL), and an extension installed without a complete `/etc/pi` is reported as the fail-closed state it is.

- Review fixes (cubic/codex on PR #2): the guard now judges both the path as written and its symlink-resolved target through the deepest existing parent (a `.env` symlink to a benign file and a new file under a symlink to `~/.ssh` are both caught); paths are normalised the way pi's tools do it (`@` prefix, `file://`, `~`, unicode spaces); `grep` applies the read deny set to explicit file targets, rejects globs that would re-include secret names (ripgrep's last-glob-wins undoes the config), defaults to the cwd when no path is given, and is blocked outright when `/etc/pi/ripgrep.conf` is missing; ripgrep.conf excludes the wallet directories; `sandbox.sb` also denies `file-link` on credential paths; a `shellPath` that already points at the wrapper no longer recurses. Documented rather than fixed: a **pre-existing hard link** to a credential file at an allowed path still reads — both Seatbelt and the guard decide by path. The Codex probe in verify-install.sh now uses a runtime `~/.codex-probe.*/.env` fixture and `/etc/hosts` control and requires the kernel's "Operation not permitted", so a missing `~/.ssh/<key>.pub` can no longer pass as a denial.


- Add Layer 0f: a Hermes managed-scope template (`managed-settings/hermes.yaml` → `/etc/hermes/config.yaml`). Hermes was the one agent harness in the baseline with no managed settings at all. Its managed scope pins config keys above the user config, the user `.env` and the shell environment, enforced by root ownership of the file.

  The load-bearing key is `approvals.deny`, the only unconditional lever Hermes exposes — matching terminal commands are blocked before `--yolo`, `/yolo` and `approvals.mode: off` are consulted. Verified by running the shipped template as a managed layer against a deliberately hostile user config (`mode: off`, `deny: []`): all eight credential-read probes still denied, and denied nothing with the managed layer removed. The `.env` rules use a character class (`*.env[!a-z0-9_-]*`) rather than a bare `*.env*`, so `cat .env && ls` denies while `prod.envelope` and `my-environment.md` stay allowed — 12 deny rules, 8/8 malicious blocked, 6/6 benign untouched.

  Scope limits are documented in the template and README rather than implied: Hermes has no path-based read guard, so this covers the `terminal` tool only and not Hermes' own file-read tool; path traversal (`cat ~/.config/../.ssh/id_rsa`) defeats it; and anyone who can set `HERMES_MANAGED_DIR` bypasses the layer.

- verify-install.sh gains Layer 0f checks, including the first **behavioural** probe in the script: `hermes approvals test` evaluates the real runtime guards without executing, prompting, or persisting anything. It asserts both directions — a `~/.ssh` read must deny *and* a benign `prod.envelope` read must not — because a rule set can fail by being too broad as easily as too narrow.

- Fix three `deny_read` entries in the Codex template that never matched anything: `**/.env`, `**/.env.*` and `**/.npmrc` are re-rooted as `~/**/.env`, `~/**/.env.*` and `~/**/.npmrc`. Codex requires filesystem paths to be absolute, `~/`-rooted or `:`-prefixed; the permission-profile parser rejects the bare form outright, but `requirements.toml` accepted it silently, so a quarter of the deny list was inert while `verify-install.sh` reported PASS. Probe files at `$HOME/<dir>/.env` and a workspace `.env` were readable under managed settings before the fix. Verified on codex-cli 0.147.0, macOS 15.3.

- Add `allowed_permission_profiles` to the Codex template. Codex 0.147 resolves write scope through named permission profiles, an axis `allowed_sandbox_modes` does not cover, and the template left it unconstrained — a profile defined in the user-writable `~/.codex/config.toml` (`"~/" = "write"`) obtained write access to all of `$HOME` with managed settings loaded. Read denials held throughout, so this widened writes only. The allowlist includes `repo-git`, the audited `.git` relaxation; drop that entry if you do not install the companion user profile.

  Two schema traps, both found the hard way and both fatal to Codex startup: the key is a **map of profile name to bool**, not a list (a list fails the requirements layer with `invalid type: sequence, expected a map`), and every profile it names must already be defined — including ones that live in user config — or Codex refuses to start with `refers to undefined profile`. Install the user-config profile first. Note also that appending a bare `key = value` to the end of this file nests it under `[permissions.filesystem]` and is silently ignored; use a table header.

- Document that `managed-settings/gemini.json` was removed intentionally (in the earlier "cleann up" commit): Gemini CLI has been retired by Google, so the repo no longer ships a Gemini managed-settings template.

- Fix the Cursor MCP deny hook missing secret paths embedded in command strings: the `.env`/`.ssh`/`.aws` patterns only matched at line boundaries of the final JSON field (no `re.MULTILINE`) and did not accept whitespace as a path boundary, so payloads like `read .env` or `cat ~/.env secrets` were allowed. The hook's argv plumbing was fine — `verify-install.sh`'s `.env` test payload now denies as intended.
